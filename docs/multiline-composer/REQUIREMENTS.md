# Multiline Composer — Requirements

## Goal
Let users compose multiline messages. On macOS, Enter sends the message and Shift+Enter inserts a new line. On iOS, Enter inserts a new line and the Send button submits the prompt.

## Scope
### In Scope
- Explicit keyboard behavior for the shared native SwiftUI session composer, with macOS delivery first and platform-specific iOS newline behavior.
- Multiline editing, pasting, bounded editor growth, accessibility, icon-only Send and keyboard/touch cancellation.
- UI-local draft ownership, submit-only text snapshots and reducer-controlled clearing by string comparison.
- Regression coverage through the existing Flux, integration and native UI test boundaries.

### Out of Scope
- Markdown preview, rich-text editing, attachments, message history navigation or configurable shortcuts.
- Steering, queued messages, sending during generation, draft persistence or new SDK/server behavior.
- Redesigning the conversation screen, settings or connection lifecycle.

## Requirements
- R1. The message input must accept and display multiple lines, including pasted text. Preserve internal newlines, blank lines and indentation when submitting; do not trim the submitted payload. Whitespace-only drafts, including newline-only drafts, remain unsendable.
- R2. On macOS, with the composer focused and sending allowed, an unmodified Enter/Return must invoke the existing send action exactly once, without inserting a newline. Both a single-line and a multiline draft must be sendable this way.
- R3. With the composer focused and editing allowed, Shift+Enter/Return must insert one newline at the caret, replacing any current selection, without sending. Normal caret movement, selection, editing, copy/paste and undo must continue to work.
- R4. On macOS, Enter must use the same eligibility and submission path as the Send button. When sending is unavailable, Enter must neither submit nor modify the draft. Pending admission, generation, stopping, disconnected and connecting states must retain their existing guards; repeated Enter must not create concurrent submissions.
- R5. Preserve admission semantics: clear the submitted draft only after confirmed admission, retain it on rejection or uncertain outcome, and never replay it automatically. Preserve the existing protection against clearing a newer draft. Keyboard handling must not duplicate controller or SDK logic.
- R6. Keyboard interception must be local to the focused composer. Enter used to confirm marked text during input-method composition must not send; users must be able to finish composing text before explicitly submitting. Do not add a window-global shortcut or hijack Enter in settings or other controls.
- R7. Preserve the current compact layout: two visible lines minimum, growth to five visible lines, then internal vertical scrolling with the caret kept visible. Long lines wrap without horizontal scrolling. Keep the icon-only Send control visible and usable. Remove the separate Stop button; macOS Esc cancels an eligible run, and iOS uses a stop icon in place of Send during a run.
- R8. Keep keyboard focus in the composer after an admitted send when editing becomes available again, unless the user has moved focus elsewhere. Shift+Enter and ordinary draft updates must not reset the caret or selection. Preserve the existing Message accessibility label and messageField identifier, plus sendButton and the iOS running-state stopButton identifier.
- R9. Show no keyboard or routine composer hints. Use an up-arrow Send icon with native accessibility label Send and explicit pointer/touch submission. Preserve connection status and error feedback. macOS Esc invokes the existing guarded Stop action during a run; ignore repeats, pending admission and stopping. Do not intercept input-method cancellation or Escape in settings/dialogs. On iOS, the same action position becomes an accessible stop icon during a run; there is no separate Stop button.
- R10. Keep the editable draft in composer-local SwiftUI state, not SessionFeature. Typing must not dispatch draftChanged actions or forward text to the store. SessionComposer may own local editing state but remains independent of Flux, dependency resolution and SDK access; the container bridges plain values/callbacks to the feature. The controller remains the effect owner. Native editor storage is presentation machinery, not a second application draft model.
- R11. Verify actual key events in native UI tests, not just direct invocation of the send callback. Cover macOS Enter submission, Shift+Enter at a caret and over a selection, pasted multiline input without automatic sending, whitespace-only input, duplicate Enter during pending admission, and retained multiline drafts after rejection/uncertain outcomes. On iOS, verify Enter inserts a newline without sending and only the Send button submits, for software and hardware keyboards. Verify input-method composition manually if reliable automation is unavailable, recording that limitation.
- R12. Use the existing semantic app.chat test drivers with lowerCamelCase actions and assertions. Keep selectors and platform-specific key-event handling in the UI driver; use integration fixtures to assert the exact submitted multiline payload and admission behavior. Tests must use injected connections or isolated fixtures, never live sessions or model credentials.
- R13. Keep both native macOS and iOS targets building. On iOS, Enter/Return inserts a newline while editing is allowed, for both software and hardware keyboards; Shift+Enter also inserts a newline. Neither key combination sends a prompt. Submit using the Send button with the existing eligibility and admission safeguards.

- R14. Send submits the exact local draft as a string snapshot through onSend(text) and SessionController.send(text); macOS Enter invokes that same submission path. No additional submission ID or edit revision is required. The controller validates session readiness and non-whitespace content before starting one request. Feature readiness must no longer depend on stored draft text; the UI combines readiness with local content validation to enable Send.
- R15. The reducer owns the decision to clear: after confirmed admission, expose clearDraftMatching: String? containing the submitted snapshot. On an accepted new submission, reset it to nil before awaiting admission so consecutive submissions of identical text remain distinguishable. Definite rejection and uncertain outcomes produce no clear instruction. Keep existing session-generation guards so obsolete results cannot clear a different session's draft. The submitted snapshot may appear in actions and the clear instruction; it is not an editable draft stored in Flux.
- R16. The container passes the optional clear instruction as a value. When a new non-nil instruction arrives, the composer clears only if its current text equals that snapshot. Do not reapply an old instruction on every keystroke or render, or on view recreation. Retain different text. String equality intentionally treats text edited away and back to the submitted value as the same draft; do not add identity/revision machinery for that case. Consume/reset the instruction after handling it through a callback/action, with no draft text updates sent while typing.
- R17. Verify no store action is dispatched while typing; whitespace-only submission is rejected at both UI and controller boundaries; success clears matching local text; different local text survives; rejection/uncertainty retain the draft; identical consecutive successful submissions both clear; consumed instructions do not clear retyped text; and stale-session results are ignored. Draft/caret assertions belong to native UI tests now that the store does not own text; integration tests submit explicit snapshots and assert admission decisions and exact payloads.

## Assumptions
- Confirmed: Enter-to-send applies only to macOS. On iOS, Enter inserts a newline and prompts are submitted using the Send button.
- The two-to-five-line editor size is retained. Approved revision 2 removes hints and the separate Stop button and uses an up-arrow Send icon; macOS uses Esc to stop and iOS replaces Send with a stop icon while running.
- Confirmed: editable draft text is local UI state. Only submission forwards a text snapshot; the reducer decides clearing using that snapshot, without submission IDs or edit revisions.
- Existing session-readiness and admission safeguards remain authoritative; draft-dependent eligibility moves to the UI with controller-side validation. No SDK changes are needed.
- Local drafts are not persisted across view destruction or app relaunch. Session-switch draft restoration is outside this feature's scope; existing generation guards still protect against obsolete asynchronous results.
- Revision 2 of mockups/multiline-composer was approved by “looks good. implement it”, after proposing the iOS running-state stop icon. macOS automation tests are deferred by explicit user request; record the resulting verification limitation.

## Implementation Plan
### 1. Local Draft and Snapshot-Based Submission
Description: Deliver the ownership change end to end on both platforms using the existing Send button before changing keyboard handling. Remove the editable draft and draftChanged action from SessionFeature, remove setDraft and draft projection wiring, and let SessionComposer own its text locally. Change SessionScreen/container callbacks and SessionController.send to accept the submitted string. Separate session readiness from local content validation, preserving controller guards and one in-flight request. Add reducer-owned clearDraftMatching, reset it at accepted send start, produce it only on confirmed admission, and bridge instruction consumption back through the container. The composer clears only a matching snapshot and acknowledges handling without publishing typing changes. Update Flux tests, controller/integration drivers and native UI assertions to their new ownership boundaries. Verify all R14–R17 cases using injected connections, including identical consecutive sends and stale results; run PiUI and native unit/UI coverage on both platforms. Do not implement keyboard shortcuts in this slice.

### 2. macOS Multiline Keyboard Submission
Description: Depends on slice 1. Deliver the complete macOS interaction through the local composer and snapshot-based guarded controller send path. Prefer a narrowly scoped NSTextView wrapped in NSViewRepresentable for explicit native text-command handling. Handle Enter/Shift+Enter in the focused native editor's text-command path: consume unmodified Enter for submission, allow native newline insertion for Shift+Enter, and defer to the input method while marked text is active. Ignore submission key repeats, leave unrelated modifier combinations native, and do not register a window-level Return shortcut or global event listener. Preserve selection, undo and marked-text behavior; do not overwrite native text on every SwiftUI update. Retain the two-to-five-line editor, remove routine hints, use an accessible up-arrow Send icon and replace the separate macOS Stop button with guarded Esc cancellation. Work test-first with Flux/integration checks for exact multiline payloads and admission outcomes, then native UI scenarios for real key events, selection replacement, pasted content and duplicate-send prevention. Verify focus restoration, scrolling and input-method composition; run PiUI and the native Release build; add native macOS UI scenarios but do not execute macOS automation suites until the user lifts the pause. Leave iOS compiling with its current touch behavior; do not change transport, server or unrelated screen behavior.

### 3. iOS Newline Entry and Button Submission
Description: Depends on slices 1–2. Deliver and verify newline insertion for Enter and Shift+Enter on iOS hardware keyboards and Return on the software keyboard, with submission exclusively through the Send button. Retain native SwiftUI multiline input if it meets the requirements; use a UITextView adapter only if necessary. Add no Enter-to-send shortcut. Keep the same local-draft, snapshot-submission and reducer-clear contract. Replace the up-arrow action with an accessible stop icon during an active iOS run so cancellation remains touch-accessible. Extend semantic native UI scenarios for newline entry without submission, Send-button submission of the exact multiline draft, long drafts and accessibility; record any physical-keyboard checks that cannot be automated. Run PiUI, iOS native unit/UI suites and both Release builds using isolated connections. macOS native automation remains deferred by user request; retain its scenarios for a later authorized run.
